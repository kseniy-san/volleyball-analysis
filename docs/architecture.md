# Архитектура веб-системы для автоматического анализа волейбольных видео.

## 1. Введение:
Цель системы — предоставить пользователям веб-интерфейс для загрузки волейбольных видео,
их автоматической обработки с помощью нейросетей (YOLO26)
и просмотра найденных розыгрышей.

## 2. Общая архитектура:
Стек:
- **Frontend:** React
- **Backend:** FastAPI 
- **База данных:** SQLite
- **Очередь:** Redis 
- **Workers:** Celery 
- **ML-модуль:** YOLO26 + fast-volleyball-tracking
- **Запуск:** Docker Compose

**Схема потока данных:**
1. Пользователь загружает видео через React-интерфейс.
2. FastAPI сохраняет видео и создает задачу в Redis.
3. Celery забирает задачу, запускает нейросетевой анализ.
4. Результаты анализа сохраняются в SQLite.
5. Frontend опрашивает статус и отображает готовые розыгрыши.

## 3. Схема базы данных:
Схема данных включает следующие сущности: 
User, Video, ProcessingJob, Rally,
Detection (ER-диаграмма в файле **ER-диаграмма.png**).

Cвязи между таблицами:
- User (1) -> (N) Video.
- Video (1) -> (N) ProcessingJob.
- Video (1) -> (N) Rally.
- Video (1) -> (N) Detection.

## 4. Жизненный цикл видео:
Каждое видео проходит через следующие статусы:
1. `uploaded` — видео загружено пользователем.
2. `queued` — задача создана и ожидает в очереди.
3. `processing` — нейросеть анализирует видео.
4. `completed` — анализ успешно завершен, то есть розыгрыши найдены.
5. `error` — произошла ошибка при обработке.

## 5. Выбор хранения результатов нейросети:
 
Надо было рассмотреть три варианта как хранить результаты работы нейросети:

**Вариант 1. Все детекции в SQLite.**

**Плюсы:** Вся информация в одном месте, поэтому есть возможность написания сложных SQL-запросов.

**Минусы:** За одно видео нейросеть генерирует миллионы детекций. 
Это приведет к гигантскому размеру базы данных и сильному замедлению вставки и чтения.

**Вариант 2. JSON/CSV + ссылки из БД.**

**Плюсы:** База данных остается легкой, файлы можно сжать или переанализировать.

**Минусы:** Нарушается целостность данных. 
Если файл на диске будет удален или перемещен, ссылка в БД станет нерабочей. 
Усложняется резервное копирование.

**Вариант 3. В БД хранить только итоговые Rally.**

**Плюсы:** База данных остается небольшой и быстрой. 
Этого более чем достаточно для работы пользовательского интерфейса. 
Время выполнения запросов минимально.

**Минусы:** Отсутствует детальная информация о траектории мяча, 
если она понадобится для глубокой анализа в будущем.

**Обоснование выбора:**
Для нашей задачи достаточно отображать найденные интервалы. 
Поэтому выберем 3 вариант: в базе данных хранятся только итоговые сущности Rally. 
Это обеспечивает максимальную производительность и целостность данных. 
Если понадобится детальная аналитика в будущем, то
архитектуру можно расширить, добавив хранение сырых детекций в файловое хранилище.

## 6. Проверка работоспособности
Для проверки корректности создания базы данных был написан скрипт check_db.py. 
При его запуске выводится следующее:

Таблицы в базе данных:
- alembic_version
- users
- videos
- detections
- processing_jobs
- rallies

Это подтверждает, что миграции Alembic успешно применились
и структура БД соответствует спроектированной ER-диаграмме.

## 7. Выводы:
Спроектированная архитектура позволяет эффективно разделить нагрузку: 
FastAPI занимается только приемом запросов, 
Celery выполняет тяжелую ML-обработку, 
а база данных SQLite хранит только необходимые метаданные и результаты, оставаясь быстрой и надежной.
